### 1. RAG 知識庫的 Chunk 策略（`rag_index.py`）

**核心設計：函式級粒度（Function-level Chunking）**

為什麼不選「模組級」或「參數級」？

| 粒度 | 問題 | 函式級的優勢 |
|------|------|-------------|
| **模組級**（如整個 `bpy.ops.mesh`） | 資訊過多，檢索時混入無關函式，噪音大 | 精確對應單一操作，檢索相關性高 |
| **參數級**（如只取 `radius` 參數） | 語義不完整，模型不知道這是哪個函式的參數 | 自包含：函式名 + 簽名 + 參數 + 範例，模型能直接複製使用 |

**Chunk 內容結構：**
```
函式全名（含模組路徑）
├── 簽名（參數類型與預設值）
├── 功能描述（特別標註「3D列印」「流形」「水密」等關鍵字）
├── 參數列表（名稱、類型、預設值、中文說明）
├── 使用範例（可直接複製的程式碼片段）
└── 相關函式（擴展檢索召回率）
```

**檢索策略：**
- **Embedding 模型**：`BAAI/bge-m3`（多語言，中英文混合查詢效果佳）
- **索引**：FAISS Flat（小量資料用精確搜索）或 IVF（大量時用）
- **Top-K**：**3~5**（過多會引入噪音，過少會遺漏關鍵 API）
- **相似度度量**：餘弦相似度（已歸一化，內積即餘弦值）

**針對 Oloid + 3D 列印的特化：**
- 優先收錄：mesh 建立、修改器（Solidify/Boolean/Wireframe）、布林運算、STL 匯出、3D Print Toolbox
- 描述中強制包含「3D 列印」「流形」「水密」等關鍵字，提升檢索命中率

### 2. Oloid 參數化建模的數學原理（`oloid_parametric.py`）

**標準 Oloid 的數學定義：**

給定兩個半徑為 $r$ 的圓，圓心距離 $d = r$，且兩圓所在平面互相垂直。Oloid 是這兩個圓的**凸包（Convex Hull）**。

| 幾何特性 | 數值 |
|---------|------|
| 表面積 | $4\pi r^2$（與同半徑球體**完全相同**） |
| 體積 | 無簡單閉式解，數值近似 $3.052 \times r^3$ |
| 表面組成 | 兩個球面片段 + 一個可展開的直紋面 |

**參數化策略（腳本中使用）：**

由於精確的 Oloid 參數化涉及**橢圓積分**，實務上採用「兩 Sphere 變形插值」的數值近似：

```
圓 1（XY 平面，中心原點）: (r·cosθ, r·sinθ, 0)
圓 2（XZ 平面，中心偏移 r）: (r + r·cosθ, 0, r·sinθ)

表面點 = 兩圓之間的加權插值（考慮緯度 v 的過渡）
```

**非等半徑 Variant 的推廣：**

當兩圓半徑不同（$r_1 \neq r_2$）或圓心距 $d \neq r$ 時，凸包形狀改變。腳本中使用**加權插值**（weight 與半徑成正比）來近似。

**3D 列印前處理管線：**
1. `remove_doubles`：合併重複頂點（布林運算後必做）
2. `fill_holes`：填補破孔（水密性必要條件）
3. `normals_make_consistent(inside=False)`：法線朝外（切片軟體識別內外）
4. `Solidify` 修改器（可選）：設定壁厚（單位：公尺，如 2mm = 0.002）
5. 再次驗證流形性（`bmesh` 檢查每條邊是否連接 2 個面）

### 3. 自然語言 → bpy 腳本的映射邏輯（`sft_data_template.jsonl`）

SFT 樣本的設計核心：**讓模型學會「意圖 → API 組合 → 完整腳本」的映射**。

**資料格式（Alpaca / Qwen Chat Template 混合）：**

```json
{
  "instruction": "自然語言需求（含尺寸、材質、結構要求）",
  "input": "[檢索結果] 相關 API 文件片段（RAG 注入）",
  "output": "完整 bpy 腳本（含詳細步驟註解）",
  "complexity": "L3-C",
  "variant_type": "standard_oloid / unequal_radius_shell / lattice_shell / composite"
}
```

**RAG 與 SFT 的協同運作：**

| 階段 | 動作 | 目的 |
|------|------|------|
| **推理時** | 用戶輸入自然語言 → RAG 檢索 Top-3 API → 注入 `input` 欄位 | 提供模型「正確的函式名與參數」，降低幻覺 |
| **訓練時** | 30% 樣本包含檢索結果在 `input` 中 | 讓模型學會「根據檢索內容組織腳本」 |
| **生成時** | 模型輸出完整腳本 → `eval_pipeline.py` 執行驗證 | 閉環回饋，確保可執行性 |

**範本中的 4 條樣本涵蓋：**
1. **標準 Oloid**：參數化表面生成、流形修復、STL 匯出
2. **非等半徑殼體**：Boolean Union + Solidify（壁厚 2mm）+ 水密修復
3. **鏤空網格**：Wireframe 修改器 + 均勻壁厚 + FDM 優化
4. **組合結構**：雙 Oloid + 橋接圓柱 + 布林聯集

## 🚀 下一步執行建議

### Phase 1 執行順序（預計 2-3 週）

| 順序 | 動作 | 驗證標準 |
|------|------|---------|
| **1** | 執行 `python rag_index.py --output_dir ./rag_db` | 確認 FAISS 索引建立成功，檢索測試返回正確 API |
| **2** | 執行 `blender --background --python oloid_parametric.py` | 確認產生 3 個 STL 且無報錯，檢查 `/tmp/*.stl` |
| **3** | 擴充 `sft_data_template.jsonl` 至 **100 條**（參考範本格式，涵蓋不同尺寸與 variant） | 每條腳本都經過 `eval_pipeline.py` 驗證（Exec + Manifold + Watertight） |
| **4** | 執行 `python qlora_train.py --data_path sft_data_template.jsonl` | 訓練 3 epochs，觀察 loss 穩定下降 |
| **5** | 用訓練好的模型生成測試腳本，再餵入 `eval_pipeline.py` | **Exec Rate > 80%**，**Manifold Rate > 60%** |

### Phase 1 Go/No-Go 檢查點

> 若 Phase 1 結束時，模型生成的腳本 **Exec Rate < 50%**：
> - 檢查資料格式：Qwen2.5 的 chat template 是否正確（`<|im_start|>system...user...assistant`）
> - 檢查序列長度：3D 腳本是否超過 `max_seq_length=4096` 被截斷
> - 考慮在 SFT 中混入 20% L1/L2 基礎語法樣本作為「墊腳石」
